# Isolated UEFI guest preflight — 2026-10-15

Owner: VS-1918 / #575; sole release preparation PR #736. This is a feasibility
measurement for the lab, not an engine approval or qualified recovery profile.
[Inputs, firmware hashes, exact command template, seed and results](1.9-vm-lab-preflight-2026-10-15.json)
are retained separately from the earlier synthetic GPT fixtures.

## Observed execution

QEMU 11.1.1 on the development Mac emulated x86_64 using TCG, Q35, 2 vCPUs and
1 GiB RAM. Bundled non-Secure-Boot x86 UEFI firmware used a copied private NVRAM
file. The only guest disks were a disposable QCOW2 overlay and a generated
NoCloud ISO. No host devices, shared directories, credentials or network adapter
were passed. The upstream base image was kept unchanged; writes stayed in the
overlay and copied variables. No host raw device was opened.

The Debian 13 genericcloud amd64 image version 20261001-2618 was fetched over
HTTPS and matched its SHA-512 in both latest and dated upstream checksum files.
This binds the downloaded lab input; no OpenPGP verification or release-media
publisher-signing qualification is claimed. Source URLs and hashes are pinned
in the structured report rather than relying on a mutable latest alias.

The guest reached its configured script, observed `/sys/firmware/efi`, x86_64,
ext4 root and a 3 GiB virtual disk with 512-byte logical sectors. The EFI system
partition mounted as vfat. It emitted both run markers and powered off normally:
152.89 seconds total, process exit 0, no timeout. These are guest observations;
no VaultSync application or interactive desktop was exercised.

The first cloud-image boot waited approximately 120 seconds for the absent
network before proceeding. SSH service failures followed deliberate omission of
host key generation; there was no network interface or SSH exposure. These are
not passing service checks. The future offline recovery medium must avoid cloud
network/SSH dependencies; this image is a lab source, not that product medium.

## Real-image GPT integration check

QEMU converted the unchanged pinned base to a sparse regular raw file. A private
.NET harness called the Core GPT inspector at source commit `b8e1094`. It returned
LayoutInspected for 3,221,225,472 bytes / 512-byte sectors, three used partition
entries and matching primary/backup metadata. The layout fingerprint is
`09ffab230a5b866260ed382aa8a8729dcc8467d0ea13d4847657f222b1a043fa`.
This independently exercises the reader on a real producer's format, beyond the
synthetic golden fixtures. It proves neither source consistency during capture
nor filesystem correctness, boot-after-restore or physical identity.

## Reproduce and retain

Use a new private workspace. Download the pinned image and checksum list from
the report, verify the expected SHA-512 and reject external QCOW2 backing files.
Create an overlay with `qemu-img create -f qcow2 -F qcow2 -b <source> <guest>`;
copy the hashed NVRAM template rather than modifying the installed template.
Write the report's exact seed files into a private directory and make a CIDATA
ISO (this run used macOS `hdiutil makehybrid -iso -joliet`). Substitute only the
workspace and QEMU share directory in the recorded argument array. Run with a
300-second deadline and retain the serial log, exit status and marker results.
Firmware/source/tool changes require recording new hashes and measurements.
Do not attach physical devices or interpret a guest marker as recovery success.

Private inputs/logs remain in `/tmp/vaultsync-recovery-lab-20261015`: source
image/checksums, overlay, seed, firmware variables, serial log, result and host
inspection output. No VM process is left running. The public report retains a
small guest excerpt and full serial-log hash, not the large disk artifacts.
