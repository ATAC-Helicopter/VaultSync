# Isolated macOS UI validation — BUG-19040 / #819

The local sandboxed QA package aborted in `NSApplication` registration before
opening its window. Both automatic and manual launches produced the same native
stack. The macOS sandbox report identified the cause:
`deny(1) mach-lookup com.apple.coreservices.launchservicesd`.

This was a missing permission in the newly assembled private QA package. The
earlier attribution to the computer-use connection was incorrect. It is not
evidence that the existing non-sandboxed direct-download package has this fault.

The [Avalonia deployment guidance](https://docs.avaloniaui.net/docs/deployment/macos/)
documents the precise Launch Services lookup needed by a sandboxed app. The QA
builder adds that named service only, alongside app sandboxing and JIT support.
It does not disable the sandbox or library validation, allow loader overrides,
grant broad filesystem access or enable incoming/outgoing network permissions.

## Build a private QA app

Publish a completed self-contained development build first:

```bash
dotnet publish src/VaultSync.UI/VaultSync.UI.csproj -c Release -f net10.0 \
  -r osx-arm64 --self-contained true -p:TargetFrameworks=net10.0 \
  -p:UseSharedCompilation=false -o /tmp/vaultsync-qa-published

python3 scripts/build_macos_qa_app.py \
  --publish-dir /tmp/vaultsync-qa-published \
  --output '/tmp/VaultSync Recovery QA.app' \
  --bundle-id dev.vaultsync.qa.recovery-local \
  --version 1.9.0
```

Use a fresh QA identifier for an independent run. Only `dev.vaultsync.qa.*` and
`dev.vaultsync.recovery.*` identifiers are accepted; the canonical product identity
cannot be selected. macOS provides that identifier's private container; config
also explicitly resolves inside it. The normal application and its projects,
backups and runtime lock are separate. Existing output apps are never replaced.
The builder rejects recursive/aliased inputs, missing native runtime files,
non-Mach-O launchers, missing execute permission and runtimes below the shared
repository security floor. A failed build removes only its newly created output.

The builder verifies its local ad-hoc signature and does not launch the app. Open
it from the desktop session or the connected UI control. Keep reports on the
device for a synthetic QA run. This development build retains policy-1 opt-in;
it is not a compiled beta/default-sending test. A sandboxed QA package is not a
backup/restore, updater, Mac App Store, publisher-signing or release qualification.
Do not publish it as a candidate/beta asset or replace the distribution builder.

## Native regression verification — 2026-10-26

The manually corrected package and a separate package generated by the new
script both opened the diagnostics choice, completed first-run onboarding and
rendered the Recovery page on native macOS arm64. The fresh profiles contained
zero projects and no destinations. Reports were explicitly kept local. Real
window captures are retained in the private editorial workspace, not GitHub.
The disk-image panel correctly shows the Linux x64 requirement on macOS and
does not claim to have restored a disk.

Six focused Python cases protect the exact entitlement, container/identifier
isolation, existing-output preservation, serviced self-contained inputs,
symlink/recursive-output refusal and signing-failure cleanup. Native launch and
rendered review supplement these tests; signature verification alone did not
prove the earlier package could launch. See the
[technical receipt](release-evidence/1.9-macos-qa-launch-2026-10-26.json).
